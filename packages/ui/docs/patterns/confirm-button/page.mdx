## Usage

```tsx
import { ConfirmButton } from "@pp/ui/confirm-button";

<ConfirmButton.Root>
  <ConfirmButton.DeleteTrigger aria-label={m.comments_delete_aria_label()} />
  <ConfirmButton.Confirm>
    <ConfirmButton.Action
      cancelLabel={m.common_cancel_button()}
      describeError={describeCause}
      prompt={m.comments_delete_confirm()}
      label={m.common_delete_confirm_button()}
      busyLabel={m.common_deleting_button()}
      onConfirm={() => remove()}
    />
  </ConfirmButton.Confirm>
</ConfirmButton.Root>;
```

`Root` holds the state. `Trigger` (any button) or `DeleteTrigger` (the trash icon) opens the confirm step; `MenuItem` opens it from a dropdown menu. `Confirm` shows the step over the trigger's row as a capsule, or in its place with `Root flow`. `Popover` shows it in a popover anchored to an element. `Action` is the prompt with its buttons. `onConfirm` may return an Effect `Exit`: a failure shows `describeError(cause)` in place of the prompt and keeps the step open.

`Root` props:

| Prop   | Type      | Default | What it does                                                         |
| ------ | --------- | ------- | -------------------------------------------------------------------- |
| `flow` | `boolean` | `false` | The step takes the trigger's place in the layout and may wrap; needed for stacked and typed steps outside a popover |
| `bare` | `boolean` | `false` | No wrapping span, for menus and popovers that position the step      |

`Action` props:

| Prop            | Type                                     | Default         |
| --------------- | ---------------------------------------- | --------------- |
| `prompt`        | `ReactNode`                              |                 |
| `label`         | `ReactNode`                              |                 |
| `cancelLabel`   | `ReactNode`                              |                 |
| `describeError` | `(cause: Cause<E>) => string`            |                 |
| `onConfirm`     | `() => Promise<Outcome> \| Outcome`      |                 |
| `busyLabel`     | `ReactNode`, read by screen readers while busy | `label`   |
| `description`   | `ReactNode` (stacked and menu layouts)   |                 |
| `layout`        | `"inline" \| "stacked" \| "menu"`        | `"inline"`      |
| `tone`          | `"destructive" \| "neutral"`             | `"destructive"` |
| `timeout`       | `number` (seconds) or `false`            | `4`             |
| `typed`         | `string`, text to type before confirming |                 |
| `waiting`       | `boolean`, busy state from outside       |                 |
| `error`         | `ReactNode`, error from outside          |                 |
| `disabled`      | `boolean`                                | `false`         |
| `size`          | `"sm" \| "xs"` (inline with `flow`)      | `"sm"`          |

`Trigger` and `DeleteTrigger` take `persist` to stay visible while confirming. `Confirm`, `Popover` and `MenuItem` take a key (`when`, `confirm`) so one root can hold several confirm steps.

## Rules

### The step slides over the row, it doesn't replace the trigger

The old step swapped the trigger for a prompt and two buttons, so the row reflowed: neighbours shifted and descriptions rewrapped. Now the trigger keeps its slot (faded and `inert`), and the step is a capsule pinned to the trigger's end edge. It always lays out at its full width and is revealed by a clip from its start edge, from the trigger's width to all of it (260ms, `ease-standard`), so its content never squeezes. It covers what is to its start side, never pushes it, and what it covers fades out toward it over 24px (a gradient to the background under the capsule, read when it opens), so text never ends in a hard cut. Closing is quicker (180ms): the clip snaps back to the trigger and the capsule stays solid until the last 80ms, then fades, so there's no slow crossfade over the trigger. Only the start edge is cut, softened by a mask up to 12px wide that narrows as the reveal ends; the other edges sit outside the clip, so the capsule's own squircle corners render throughout. The clip is measured in layout pixels, so it also holds inside a CSS `zoom`.

### The capsule is a popup

It floats over content, so it uses the popup surface every popup shares: card fill and a 60% hairline, no shadow. It is 32px tall, 2px past a 28px trigger on each side, with 24px buttons on a 4px inset, so the row's height never changes. The prompt, confirm and Cancel rise in after it with a 30ms stagger and a small blur; with reduced motion they only fade.

### A destructive step closes by itself after 4 seconds

An open confirm left behind is a loaded button. The confirm button's red fill is the timer: it waits for the capsule to land, then drains toward the start over 4 seconds and closes the step. It is Button's `countdown`, so the look and the hold rules are Button's. Pointer over the capsule holds it. Keyboard focus inside it holds it too, for as long as it stays, so keyboard and screen reader users never run out of time (WCAG 2.2.1). Busy and error states stop it. Neutral confirms don't count down, because their primary fill doesn't read once it drains. `timeout` changes the time or turns it off.

### Focus goes to Cancel, and comes back to the trigger

The step opens from a click, so Cancel takes focus: Enter cancels, and Shift+Tab reaches the confirm. Esc closes the step, and focus returns to the trigger after Esc, Cancel, or the timeout. Cancel is an icon in the capsule, with its label for screen readers.

### Busy uses Button's loader

While `onConfirm` runs, the confirm button shows Button's `loading` state: the logo loader over its label, which keeps the button's width, so nothing in the capsule moves. Cancel disables, the countdown holds, and screen readers hear `busyLabel` ("Deleting…").

### Errors replace the prompt

A failed `onConfirm` rolls the prompt into the error through TextSwap, and the colour eases to destructive; the capsule follows the new width, growing from its end edge. The step stays open with no countdown, so the person can retry or cancel, and a retry rolls the prompt back. The error is also read out as an alert, since TextSwap's text isn't announced when it changes.

### Wording

The prompt is a question that names what goes ("Delete this comment?", "Delete for everyone?"). The confirm repeats the verb ("Delete", "Delete project", "Disconnect"), never "OK" or "Yes".

### Long prompts and narrow places use `flow`

When the prompt names something long or the row is narrow (library entries, bulk delete, the organization's typed delete), `Root flow` keeps the older in-place step, which may wrap onto a second line. Menus open the stacked step in a popover on the menu's button, with a title, one line of consequence, and the action on the end.
