# Jira Cloud project migration research

Date: 2026-09-14

## Conclusion

A broad one-way migration from a Jira Cloud project is feasible. The best primary path is the Jira Cloud REST API v3, supplemented by the Jira Software Agile API for boards and sprints. It can retrieve the project, visible issues and their configured fields, comments, attachment bytes, worklogs, changelogs, relationships, and most Agile data while giving ProjectProject enough structure to report exactly what was imported, transformed, skipped, or hidden by Jira permissions.

It cannot promise a byte-for-byte or behavior-for-behavior migration. Jira only returns data visible to the authorizing user; private issues, restricted comments/worklogs, watcher and voter identities, workflow configuration, role membership, and security configuration require additional permissions. Jira app data, automation, and some product-specific data are outside the standard export surface. Rich text must be converted from Atlassian Document Format (ADF) to Markdown, which is necessarily lossy for constructs Markdown does not model. ProjectProject also has a deliberately smaller domain model than Jira.

The product should call this a **Jira migration**, not a sync or integration: it creates a new ProjectProject project from a point-in-time Jira project and produces a migration report. No ongoing relationship is implied.

## Recommended extraction approach

### 1. REST API v3 plus Jira Software Agile API

This is the recommended product path.

Use OAuth 2.0 authorization-code flow (3LO) for a user-facing feature. A 3LO app acts on behalf of a user, and the user's own Jira permissions continue to constrain every response even when the OAuth token has the necessary scopes. Requests use the selected site's `cloudid` through `api.atlassian.com`. Atlassian recommends API-token basic auth only for simple scripts and manual calls, not a distributed integration. ([OAuth 2.0 3LO](https://developer.atlassian.com/cloud/jira/platform/oauth-2-3lo-apps/), [basic authentication](https://developer.atlassian.com/cloud/jira/platform/basic-auth-for-rest-apis/))

Suggested extraction sequence:

1. Resolve the Jira site and project, then preflight the current user's permissions.
2. Fetch project metadata, project issue types/statuses, fields and field metadata.
3. Page through `POST /rest/api/3/search/jql` with `project = <key>`, explicitly requesting all fields needed by the migration. The enhanced search endpoint uses a continuation token and returns only issues the caller can browse and is allowed to see under issue security. ([issue search](https://developer.atlassian.com/cloud/jira/platform/rest/v3/api-group-issue-search/))
4. Fetch separately paginated or permission-sensitive child collections: comments, worklogs, changelogs, watchers, and votes.
5. Download each visible attachment through its content endpoint.
6. For Jira Software projects, discover boards by `projectKeyOrId`, fetch board configuration and sprints, and reconcile sprint membership with issue fields. ([boards](https://developer.atlassian.com/cloud/jira/software/rest/api-group-board/))
7. Convert and validate into an intermediate migration manifest before writing any ProjectProject data. Keep stable Jira IDs and keys in the manifest so references can be resolved in a second pass.
8. Create the ProjectProject project atomically if possible, then emit counts and itemized warnings for inaccessible and lossy data.

Jira collection endpoints enforce pagination. Limits differ per operation and can change without notice, so migration code must follow each response's `isLast`, `nextPage`, or `nextPageToken` rather than assume a page size. Resource expansion is explicit; fields such as changelog or rendered content should not be assumed present unless requested or fetched separately. ([REST v3 expansion and pagination](https://developer.atlassian.com/cloud/jira/platform/rest/v3/intro))

Jira Cloud currently applies points-based hourly quotas, per-endpoint burst limits, and per-issue write limits to apps. A migration is read-heavy but must still handle `429`, honor `Retry-After`, apply backoff, and be resumable. ([rate limiting](https://developer.atlassian.com/cloud/jira/platform/rate-limiting/))

### 2. Jira Cloud site backup

A site backup is the widest official export. Atlassian says it can contain work items and system/custom field content, boards and sprints, users and group settings, comments, optional attachments/media, workflows, permissions and schemes, screens, issue types, board configuration, and Advanced Roadmaps. The archive stores database data in `entities.xml` and `activeobjects.xml`, with media in directories. ([Export data from Jira Cloud](https://support.atlassian.com/jira-cloud-administration/docs/export-issues))

This is useful as an optional administrator/offline migration path, but not the primary in-product flow:

- It is site-wide rather than naturally scoped to one project.
- It requires Jira administration and manual backup generation/download.
- Its XML and Active Objects representation is an implementation-shaped restore format, not a stable public integration contract.
- Backups containing attachments, avatars, or logos can only be created once every 48 hours.
- Team-managed projects have compatibility caveats in the Data Center backup flow.

If supported later, treat it as a separately versioned importer with fixtures from multiple Jira Cloud editions, not as a fallback parser hidden behind the REST migration.

### 3. CSV export

CSV is a useful low-privilege/manual fallback. Jira can export all fields for a project's work items, and the all-fields export includes each comment in a separate chronological `Comment` column. It does not bulk-download physical attachments; at most it provides attachment URLs that require separate authorized retrieval. ([Export issues as CSV](https://support.atlassian.com/jira/kb/how-to-export-issues-from-jira-cloud-in-csv-format/))

CSV is not suitable for the inclusive migration goal because it flattens typed field values and rich text, does not carry complete project/workflow/permission/board configuration, has awkward repeated columns for multi-valued fields/comments, and cannot reliably preserve all relationship and history semantics. It should be labeled **basic ticket import**, not full Jira migration.

## Data coverage matrix

Legend:

- **Accessible**: available through documented APIs to a normally authorized caller with project visibility.
- **Conditional**: available only when a Jira feature is enabled, the user has elevated/specific permission, the data is visible, or the project has Jira Software features.
- **Lossy / unsupported**: extractable only in part, not behaviorally portable, or not representable in ProjectProject today.

| Project identity | **Accessible.** Project endpoints expose ID, key, name, description, URL, lead, type/style, category, avatar URLs, and issue types depending on expansion and permissions. Only visible projects are returned. ([projects](https://developer.atlassian.com/cloud/jira/platform/rest/v3/api-group-projects/)) | Name and usually key map directly. Description can become project Markdown. Jira ID, URL, lead, category, style/type, avatar, and original key need provenance metadata or a report; the current project shape has no fields for them. Jira keys outside ProjectProject's 2–10 character key rules need remapping. |

Results are filtered by Browse Projects and issue-level security. ([project versions](https://developer.atlassian.com/cloud/jira/platform/rest/v3/api-group-project-versions/)) | A Jira version resembles a ProjectProject milestone group, but released/archived semantics and affected-versus-fix-version distinctions do not map exactly. Preserve both membership types if mapped. |

([users](https://developer.atlassian.com/cloud/jira/platform/rest/v3/api-group-users/)) | Jira `accountId` does not identify a ProjectProject/GitHub-authenticated user. Otherwise retain historical display name/account ID and use an importer/system author; never silently attribute content to the person running the migration. |

Jira permission grants, groups, issue levels and schemes cannot be recreated faithfully. |

## Known unavailable or inherently incomplete areas

- **Anything the authorizing user cannot see.** Jira deliberately filters issues, comments, attachments, worklogs, boards, users, watchers and voters. A successful API response does not prove completeness. The migration should run a permission preflight and display “visible to this Jira account,” never “all Jira data,” unless elevated checks support that claim. Jira's API permission model is documented in the REST introduction. ([permissions](https://developer.atlassian.com/cloud/jira/platform/rest/v3/intro))
- **Third-party app data and opaque app fields.** Atlassian's own backup documentation says third-party apps and app data are not exported. Standard custom-field values may still appear on issues, but their external configuration, semantics and linked content are not portable. ([backup exclusions](https://support.atlassian.com/jira-cloud-administration/docs/export-issues))
- **Automation behavior.** Automation rules are excluded from site backups by default and are not represented by ProjectProject. Atlassian provides a separate manual automation export, but that is not a portable behavioral contract. ([backup exclusions](https://support.atlassian.com/jira-cloud-administration/docs/export-issues))
- **Jira Service Management-specific domains.** Requests, organizations, customers, SLAs, forms, approvals, Assets, queues, knowledge links, and Opsgenie data need separate JSM APIs or are excluded from backup. They should be explicitly out of scope for the first Jira Software/Work Management migration and detected rather than silently ignored.
- **Jira Product Discovery-specific presentation.** Atlassian excludes view configurations, insights and vote fields from its site backup. ([backup exclusions](https://support.atlassian.com/jira-cloud-administration/docs/export-issues))
- **Behavioral configuration.** Notifications, dashboards, filters, screens, field layouts, workflow rules, permissions and schemes may be readable by admins or present in backup, but ProjectProject has no equivalent execution model. Archiving the configuration is different from migrating its behavior.
- **Exact rich-text fidelity.** ADF nodes such as panels, expands, statuses, mentions, media, colors and extensions have no exact Markdown representation. The converter must report unsupported nodes and preserve readable content instead of dropping whole subtrees.

## Product implications for an inclusive migration

An inclusive importer should optimize for **preservation and explicit loss**, not force every Jira concept into a first-class ProjectProject feature.

The smallest safe destination contract would need:

- a migration manifest containing source site/project IDs, source issue IDs/keys, field definitions, identity mappings, normalized extracted records, original ADF for rich-text fields, and migration version;
- a deterministic mapping preview for statuses, issue types, priorities, labels, components, versions and users;
- a provenance representation for unsupported fields/history rather than inserting a large generated appendix into every ticket body by default;
- a two-pass reference rewrite for parents, epics, links, comments and attachment URLs;
- a dry-run summary with visible issue count, expected Jira count where obtainable, inaccessible/partial categories, unsupported ADF nodes, rejected attachments and mapping collisions;
- atomic creation or a resumable staging state so a rate limit or failed attachment does not leave an apparently complete half-project;
- an explicit security warning whenever issue/comment/worklog restrictions cannot be represented.

The exact manifest location, whether it remains after migration, how Jira identities map to ProjectProject users, and whether components/versions become tags/groups are architectural and API-surface decisions. They should be chosen before implementation rather than embedded implicitly in importer code.

## Proposed first-release boundary

For a useful but honest first release, migrate:

- project name, key where valid, description and source URL;
- every issue visible to the authorized account;
- summaries, ADF descriptions converted to Markdown, created/updated dates and source keys;
- statuses with category-informed defaults;
- previewed mappings for issue types and priorities;
- labels, with normalization and collision reporting;
- multiple assignees only after identity mapping;
- epics and sprints as groups;
- comments with historical attribution preserved even when no ProjectProject user matches;
- attachment bytes and rewritten references;
- links, components, versions, worklogs, changelog, watcher/vote counts, and unmapped custom/system fields as queryable migration provenance.

Defer full workflow behavior, Jira permissions/security reproduction, boards as independent views, Jira Service Management semantics, automation, third-party app behavior, and ongoing sync. This boundary remains broad in preserved data while avoiding a claim that ProjectProject has recreated Jira itself.
