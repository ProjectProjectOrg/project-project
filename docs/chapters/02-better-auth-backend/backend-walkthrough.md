## Why each file looks the way it does

### `services/BetterAuth.ts` — bridging a Promise-based library

Every Promise-based library you wrap in Effect follows the same pattern:

- A **boundary error type** declared with `Data.TaggedError`. Internal-only — never crosses the wire.
- One **Tag** declaring the methods the rest of the app may call.
- A **Layer** using `Layer.effect` (no resource lifecycle here — Better Auth is a plain object) and `Effect.tryPromise({ try, catch })` to bridge each method.

```ts
handler: ;
;((request) =>
  Effect.tryPromise({
    try: () => auth.handler(request),
    catch: (cause) => new BetterAuthError({ cause })
  }))
```

This contrasts directly with Chapter 1's `Db` service: Drizzle's `QueryPromise` extends `Effect.Effect` via TypeScript module augmentation, so `yield* db.select()...` works without any wrapping. Better Auth ships no such helper, so we do the wrapping ourselves — once, in this file. From the rest of the app, both look the same: a yieldable Effect.

The service surface stays narrow on purpose. Better Auth's `auth.api` namespace has dozens of methods (`signInEmail`, `signOut`, `revokeSession`, …), but most of them are reached by the frontend hitting `/api/auth/...` URLs that Better Auth handles itself. Server-side we only need two: `handler` (so we can mount Better Auth under `/api/auth/*`) and `getSession` (so the middleware can resolve a cookie to a user).

### `services/Auth.ts` — the middleware Live Layer

`HttpApiMiddleware.Tag` produces a class you implement via `Layer.effect`. The shape: "for each declared security scheme, an Effect that returns the `provides` type or fails with the `failure` type."

```ts
return Authentication.of({
  sessionCookie: (_token) =>
    Effect.gen(function*() {
      const req = yield* HttpServerRequest.HttpServerRequest
      const session = yield* ba
        .getSession(req.headers as unknown as Headers)
        .pipe(Effect.mapError(() => new Unauthorized()))

      if (session === null) {
        return yield* Effect.fail(new Unauthorized())
      }
      return session.user
    })
})
```

Two subtleties:

- **The `_token` argument is unused.** The framework parses the cookie according to your `HttpApiSecurity.apiKey` declaration and hands it to you. Better Auth wants the full headers (it does its own cookie parsing, fingerprinting, etc.), so we yield the request and pass `req.headers` directly. The framework still enforces "cookie must be present" — without one, the request short-circuits with `Unauthorized` _before_ this function runs.
- **`BetterAuthError` collapses to `Unauthorized`.** The boundary error from the wrapper has nothing the client can do with it; it becomes a 401 by way of `Effect.mapError`. If we wanted server-side observability of the underlying cause, we'd `Effect.tapErrorCause` to log it before mapping.

### `handlers/auth.ts` — the thin handler

`/me` is the smallest possible handler: yield `CurrentUser`, return it.

```ts
handlers.handle("me", () =>
  Effect.gen(function*() {
    const user = yield* CurrentUser
    return user
  }))
```

The middleware did all the work before this ran. The handler is just plumbing. This is the rule throughout the app: handlers stay thin, all logic lives in services. When `/projects/:slug` shows up later, its handler will be the same shape — yield `CurrentUser`, yield the `Projects` service, call a method, return the result.

The thinness is also why `addError(Unauthorized)` on the endpoint is enough to make the wire failure-path correct. The handler itself never produces `Unauthorized`; the middleware does, and the framework knows it because it's declared in both places.

### `main.ts` — the router and the web-handler bridge

Two pieces needed gluing in `main.ts`:

**1. The Better Auth web-handler bridge.**

Better Auth speaks plain web Fetch — it expects a `Request`, returns a `Promise<Response>`. The Effect HTTP server speaks `HttpServerRequest` / `HttpServerResponse`. We need to convert each direction:

```ts
const betterAuthApp = Effect
  .gen(function*() {
    const ba = yield* BetterAuth
    const req = yield* HttpServerRequest.HttpServerRequest
    const webReq = yield* HttpServerRequest.toWeb(req)
    const webRes = yield* ba.handler(webReq)
    return HttpServerResponse.fromWeb(webRes)
  })
  .pipe(
    Effect.catchAll(() =>
      HttpServerResponse.text("Auth error", { status: 500 })
    )
  )
```

`HttpServerRequest.toWeb` is a top-level function (not a method) returning `Effect<Request, RequestError>` — it reads the body stream and constructs a standard web `Request`. `HttpServerResponse.fromWeb` does the reverse, synchronously.

**2. The router.**

The HttpApi covers `/api/*` paths via your defined endpoints. Better Auth covers `/api/auth/*`. Both need to live behind the same Bun server. `HttpApiBuilder.serve` accepts an optional middleware function: it hands you the HttpApp built from `AppApi` and you return whatever HttpApp you want served. We return a router:

```ts
HttpApiBuilder.serve((apiApp) =>
  HttpRouter.empty.pipe(
    HttpRouter.mountApp("/api/auth", betterAuthApp),
    HttpRouter.mountApp("/", apiApp),
    Effect.catchTag("RouteNotFound", () =>
      HttpServerResponse.text("Not Found", { status: 404 }))
  )
)
```

`HttpRouter.mountApp` strips the prefix before delegating to the child app, so Better Auth sees `/sign-in/github`, not `/api/auth/sign-in/github`. First match wins. The `catchTag` collapses the router's own `RouteNotFound` failure into a 404 response — without it, the type system blocks you, because `HttpApiBuilder.serve` requires the returned HttpApp's error channel to be `never`.

That requirement is itself an Effect lesson worth pausing on. The HTTP layer has no concept of "an unhandled tagged error" — every failure must be a response. The framework expresses that as "give me an HttpApp whose `E = never`", and you discover what you've forgotten to handle by reading the type error. Three sources here: `BetterAuthError | RequestError` from the auth bridge (handled by `Effect.catchAll` inside `betterAuthApp`), and `RouteNotFound` from the router itself (handled by the `catchTag`). Once all three are covered, the channel collapses to `never` and the call typechecks.

## The Effect ideas earning their keep here

- **Module augmentation vs. explicit wrapping.** Drizzle and Better Auth represent two ends of the spectrum for Promise-based libraries meeting Effect. One uses TypeScript declaration merging to make queries pretend they're Effects; the other doesn't, so we wrap. Both are normal — most libraries you'll integrate are like Better Auth.
- **Tagged middleware as typed dependency injection.** The handler doesn't read cookies, doesn't call Better Auth, doesn't even know an auth system exists — it just yields `CurrentUser`. The middleware Layer is the only thing that knows about cookies and Better Auth. Forgetting `.middleware(Authentication)` on a group becomes a _type error_ in the handler (because `CurrentUser` is no longer in the resolved context), not a security hole.
- **`E = never` as a forcing function.** The router exposing every unhandled error in its type signature is the system telling you "you haven't decided what these failures look like to the user yet." It's Effect's pattern for putting the decision back where it belongs — in your code, not in framework defaults.

## Things to watch out for

- **`HttpApiSecurity.apiKey` with `in: "cookie"` and a cookie name.** The cookie name in your shared `Authentication.ts` must match what Better Auth actually sets. In dev you'll see `better-auth.session_token`; in production behind HTTPS the prefix may change to `__Secure-better-auth.session_token`. Inspect the cookie in devtools after the OAuth round-trip to confirm.
- **`req.headers` typing.** Effect's `HttpServerRequest.headers` is a `Record<string, string>`, not a `Headers` instance. Better Auth's API accepts both shapes, but the TypeScript types are mismatched, which is why `services/Auth.ts` does `req.headers as unknown as Headers`. Annoying but harmless — runtime accepts the record.
- **`ApiLive` carries `BetterAuth` in its requirements** (because `AuthenticationLive` does). That means any test that constructs a handler from `ApiLive` must provide a `BetterAuth` layer, even if the test only exercises an endpoint that doesn't touch auth. `main.test.ts` uses a `FakeBetterAuthLive = Layer.succeed(BetterAuth, {} as never)` stub — calling into it would crash, which is the right failure mode for a misrouted test.
- **Routing order matters.** The router checks mounts in declaration order; first match wins. If you ever swap the lines so `/` comes before `/api/auth`, the catch-all will swallow auth requests. There's no test for this — _the convention_ is the safety.
