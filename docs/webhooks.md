# Outbound webhooks

A project can send signed HTTP requests to URLs you choose when something
happens in it, for example when a ticket changes status. Use them to wake an
agent, notify another tool, or start a CI job.

Project PMs manage webhooks under project settings. Each webhook has a URL,
the events it subscribes to, optional extra headers, and a signing secret.

## Setting one up

- **URL:** must use `https`. It may not contain a username or password, and it
  must resolve only to public addresses (see [Address checks](#address-checks)).
  PP stores the URL encrypted and afterwards shows only its scheme and host,
  because many receivers put a token in the path.
- **Events:** one or more of the [event types](#events).
- **Extra headers:** up to 10, e.g. `Authorization: Bearer …`, with printable
  ASCII values. Stored encrypted
  and shown by name only. They can't replace the headers PP sets itself:
  `Host`, `Content-Type`, `Content-Length`, `User-Agent`, connection headers,
  and anything starting with `X-PP-` or `Webhook-`.
- **Signing secret:** generated by PP and shown once, when you create the
  webhook or rotate its secret. Rotation takes effect immediately; update the
  receiver straight away.

## Requests

Each delivery is a `POST` with a JSON body:

```json
{
  "id": "0193a1f2-…",
  "type": "ticket_status_changed",
  "createdAt": "2026-11-01T12:00:00.000Z",
  "org": { "slug": "acme" },
  "project": { "slug": "web", "url": "https://pp.example.com/orgs/acme/projects/web" },
  "actor": { "id": "user-id", "name": "Ada" },
  "data": {
    "ticket": {
      "id": "T-12",
      "title": "Ship it",
      "status": "in_progress",
      "type": "feat",
      "url": "https://pp.example.com/orgs/acme/projects/web/tickets/T-12"
    },
    "previousStatus": "todo"
  }
}
```

`createdAt` is when PP recorded the event. `actor` is `null` when no user
caused it. The body carries ids and links rather than ticket descriptions;
fetch more through the MCP server or the `pp` CLI if you need it.

Requests follow [Standard Webhooks](https://www.standardwebhooks.com/), so
any of its libraries can verify them. Headers:

| Header | Value |
| --- | --- |
| `Content-Type` | `application/json` |
| `User-Agent` | `ProjectProject-Webhooks/1` |
| `webhook-id` | The delivery id, the same as the body's `id` and the same on every retry |
| `webhook-timestamp` | When this attempt was sent, in Unix seconds |
| `webhook-signature` | `v1,` followed by the base64 HMAC-SHA256 of `{webhook-id}.{webhook-timestamp}.{raw body}`, keyed with the secret's bytes (the part after `whsec_`, base64-decoded) |
| `X-PP-Event` | The event type, e.g. `ticket_status_changed`, or `ping` |
| `X-PP-Signature-256` | `sha256=` followed by the lowercase hex HMAC-SHA256 of the raw body, keyed with the whole secret string. For receivers that can only check a body signature, such as GitHub-style webhook tools |

### Verifying the signature

Use a Standard Webhooks library where you can, with the signing secret as is:

```ts
import { Webhook } from "standardwebhooks"

const payload = new Webhook(secret).verify(rawBody, headers)
```

It checks `webhook-signature` over the exact bytes you received and rejects
timestamps more than five minutes off, which stops replayed requests. To verify
by hand, compute the same HMAC before parsing the body and compare in constant
time:

```ts
import { createHmac, timingSafeEqual } from "node:crypto"

const verify = (
  secret: string,
  id: string,
  timestamp: string,
  rawBody: string,
  header: string
) => {
  const key = Buffer.from(secret.replace(/^whsec_/, ""), "base64")
  const expected = createHmac("sha256", key)
    .update(`${id}.${timestamp}.${rawBody}`)
    .digest("base64")
  const age = Math.abs(Date.now() / 1000 - Number(timestamp))
  return (
    age < 300 &&
    header.split(" ").some((part) => {
      const given = Buffer.from(part.replace(/^v1,/, ""))
      const wanted = Buffer.from(expected)
      return given.length === wanted.length && timingSafeEqual(given, wanted)
    })
  )
}
```

`X-PP-Signature-256` covers only the body, so it doesn't protect against
replays. Use it only when the receiver can't check `webhook-signature`, and
deduplicate on `webhook-id`.

### Duplicates

Delivery is at least once. A request that times out may still have arrived,
and PP then sends it again with the same `webhook-id`. Keep delivery ids for at
least a day and ignore ones you have already handled.

## Events

| Event | When | `data` |
| --- | --- | --- |
| `ticket_created` | A ticket is created | `ticket` |
| `ticket_status_changed` | A ticket moves to another status | `ticket`, `previousStatus` |
| `ticket_completed` | A ticket moves into a finished status | `ticket` |
| `ticket_reopened` | A ticket moves out of a finished status | `ticket` |
| `ticket_assignees_changed` | Assignees are added or removed | `ticket`, `assignees`, `added`, `removed` (user ids) |
| `sprint_created`, `sprint_renamed`, `sprint_started`, `sprint_completed`, `sprint_reopened`, `sprint_deleted` | Sprint changes | `sprint` with `id`, `title`, `startsAt`, `url` |
| `ping` | You click "Send test event" | `{}` |

A ticket moving into a finished status sends both `ticket_status_changed` and
`ticket_completed` to webhooks subscribed to both. Archived tickets send no
events. `ticket.type` is `null` on events recorded before PP captured types.

## Retries

PP sends one request at a time per webhook, oldest first.

| Response | What PP does |
| --- | --- |
| `2xx` | Delivered |
| Network error, timeout, `408`, `429`, `5xx` | Retries later with the same delivery id |
| Any other status, including redirects | Marks the delivery failed and doesn't retry it |

Each attempt has 10 seconds, DNS lookup included. Redirects are not followed.
PP reads at most 64 KiB of the response and keeps a short, redacted excerpt for
the delivery log. Request bodies are at most 1 MiB.

After a failed attempt the whole webhook waits before its next request: 10
seconds, doubling up to an hour, or longer if the response had a `Retry-After`
header. Any success resets this. PP sends at most one request per second to a
webhook. Deliveries not sent within 24 hours are marked expired.

A webhook is disabled automatically after three `404` or `410` responses in a
row, or after 10 failed attempts spanning at least 6 hours. Settings show why.
While disabled it receives no new events. Enabling it again resets the failure
count and sends anything still within the 24-hour window.

## Delivery log

Settings list each webhook's recent deliveries: event, state, attempts, last
status code or error, and a response excerpt. PP keeps the latest 50 deliveries,
10 test pings and 20 expired deliveries per webhook, so an outage can't push
out older history. From the log you can:

- **Send test event:** queues a `ping` through the normal signing path.
- **Retry now:** resets the webhook's failure count. A pending delivery is
  tried as soon as the per-second limit allows; a failed or expired one is
  queued again, with the same delivery id, if it is less than a day old.

A PM can also disable a webhook by hand. It keeps its settings and log,
receives no events while disabled, and can be enabled again.

## Address checks

The server sends requests to URLs that users enter, so it refuses addresses
inside a network: private, loopback, link-local, carrier-grade NAT, multicast,
documentation and reserved ranges, IPv6 unique-local addresses, and IPv6 forms
that embed such an IPv4 address. PP checks every address a host name resolves
to, connects only to the address it checked, and checks again on every
attempt, so a DNS change can't redirect a webhook inside your network.

Self-hosted installations that need to reach internal services can set
`WEBHOOKS_ALLOW_PRIVATE_NETWORKS=true`. This also allows plain `http` URLs.
Leave it off on any installation where people you don't fully trust can manage
project settings.
